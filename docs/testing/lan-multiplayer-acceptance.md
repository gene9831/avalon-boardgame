# Avalon LAN 多客户端人工验收

本文档用于一个测试者通过彼此隔离的浏览器 Profile 和局域网设备，逐步验证 5–10 人 Avalon MVP。测试结果只有在实际执行后才能记录为通过；自动化测试、单页面预览和多个普通标签页不能替代本手册。

## 1. 验收门槛

按以下顺序执行，不要在首次流程测试中同时注入刷新、断网或服务重启：

1. **Gate A：5 人功能闭环**——中央操作区、角色可见性和四种结束路径。
2. **Gate B：刷新与持久化重连**——分别验证选队、投票、任务牌、Node 服务重启和 PostgreSQL 服务重启。
3. **Gate C：7–10 人 LAN**——7 人特殊任务、10 人容量、真实设备和双房间隔离。

只完成 Gate A 时，只能记录“5 人流程通过”；完成 Gate C 后才能记录“5–10 人 LAN 验收通过”。

## 2. 测试前准备

### 2.1 浏览器隔离

为每名玩家使用永久且彼此隔离的浏览器 Profile，不要使用同一 Profile 的普通标签页或同一无痕会话。

| Profile | 玩家名称 | 初始用途 |
| --- | --- | --- |
| P1 | `QA-P1` | 房主 |
| P2 | `QA-P2` | 玩家 |
| P3 | `QA-P3` | 玩家 |
| P4 | `QA-P4` | 玩家 |
| P5 | `QA-P5` | 玩家 |
| P6–P10 | `QA-P6`–`QA-P10` | Gate C 扩容 |

### 2.2 启动服务

首次配置环境时先完成以下预检：

1. 按 [`infra/postgres/README.md`](../../infra/postgres/README.md) 启动 PostgreSQL，并确认容器健康；使用其他 PostgreSQL 部署时执行等价检查。
2. 将 `apps/server/.env.example` 复制为 Git 忽略的 `apps/server/.env.local`。
3. 在 `.env.local` 中设置真实的私有 `DATABASE_URL`，不要把密码写入本文档或终端截图。
4. 添加允许实际 Web 来源的配置。只在本机测试时至少包含 `http://localhost:5183`；使用 LAN 设备时再加入主机 IP 来源：

   ```env
   AVALON_ORIGINS=http://localhost:5183,http://<运行 Web 的主机 IP>:5183
   ```

5. 需要测试房间清理时，在 `.env.local` 中启用 `AVALON_DEV_TOOLS=true` 并设置非空的私有 `AVALON_DEV_ADMIN_TOKEN`。

不要使用服务端默认的 `http://localhost:5173` 验收本项目；当前 Vite 端口是 5183。完整环境变量说明见 [`apps/server/README.md`](../../apps/server/README.md)。

在两个由测试者保持打开的终端中，从仓库根目录启动：

```bash
# 终端 1：boardgame.io 游戏服务和 Lobby API
pnpm dev:server

# 终端 2：Vite Web
pnpm dev
```

本机 Profile 打开：

```text
http://localhost:5183/
```

局域网设备打开：

```text
http://<运行 Web 的主机 IP>:5183/
```

预期结果：

- Web 使用 5183，游戏服务使用 8000，Lobby API 使用 8001。
- 五个 Profile 都能打开主页并看到房间列表。
- PostgreSQL 在 Gate A 和 Gate B1–B4 期间保持运行；只在 B5 按步骤安全重启。
- 服务端正常连接 PostgreSQL，控制台没有数据库连接或 CORS 错误。
- `AVALON_ORIGINS` 已包含实际访问 Web 的来源。

### 2.3 测试房间清理

开发管理工具只用于删除失败或已记录完成的测试房间，不得用来修改游戏状态。管理员 Token 只从本机 `apps/server/.env.local` 输入页面，不得写入本文档、截图、聊天或浏览器持久化存储。

游戏开始后不要尝试普通离座；需要放弃该局时，记录证据后通过开发管理工具删除房间，再创建新房间。

### 2.4 失败记录模板

```text
测试编号：
房间 ID：
玩家 Profile / 座位：
当前阶段：
上一个成功动作：
本次动作：
预期结果：
实际结果：
按钮状态：禁用 / 可用但无响应 / 报错
其他客户端状态：
Console 错误：
截图路径：
```

第一次出现异常时立即停止该局。不要在同一局继续叠加刷新、断网或服务重启。

## 3. Gate A：5 人功能闭环

### A0. 中央操作区冒烟测试

1. P1 创建 5 人房间，名称使用 `QA-P1`。
2. P2–P5 依次选择空座位，使用各自固定名称加入。
3. P1 确认五个座位均已连接后开始游戏。
4. 当前队长点击两个座位。5 人局第 1 次任务需要 2 人。
5. 确认中央按钮显示 `提交 2/2`，然后点击提交。

预期结果：

- 点击外围座位后，座位显示“任务队员”。
- 只选 0 或 1 人时提交按钮禁用；选满 2 人后按钮启用。
- 点击 `提交 2/2` 后，五个客户端都进入队伍投票阶段。
- 页面没有停留在选队阶段，也没有只有部分客户端进入投票。

记录 A0 结果后，通过开发管理工具删除该冒烟房间，再为 A2 创建新房间。

### A1. 开局角色与信息边界

测试者可以查看五个 Profile 并在测试记录中记下角色映射，但每个页面仍必须满足以下预期：

| 当前角色 | 开局允许看到的信息 |
| --- | --- |
| Merlin | 自己是 Merlin；看到邪恶玩家，但不知道对方的具体邪恶角色 |
| Assassin | 自己是 Assassin；知道另一名邪恶玩家 |
| Minion | 自己是 Minion；知道 Assassin |
| Loyal Servant | 只知道自己的角色和 Good 阵营 |

所有客户端都不得看到其他玩家的待提交投票或任务牌。

### A2. Good 胜利：刺客未命中 Merlin

5 人局五次任务人数依次为 `2 / 3 / 2 / 3 / 3`。

1. 从新房间开始并记录角色映射。
2. 每次由界面标记的当前队长选择所需人数。
3. 五名玩家依次投“同意队伍”。
4. 只有任务队员提交任务牌；前三次任务全部提交 Success。
5. 每次结算后检查中央任务板，再继续下一次提案。
6. 三次任务成功后，由 Assassin 选择一名不是 Merlin 的 Good 玩家。

预期结果：

- 每名玩家只能看到自己的投票提交状态；全员提交后才公开投票结果。
- Good 玩家只有“让任务成功”；Evil 玩家同时拥有 Success 和 Fail。
- 非任务队员不能提交任务牌。
- 任务结算只显示 Success/Fail 数量，不关联玩家。
- 三次任务成功后进入刺杀阶段。
- 刺杀未命中 Merlin 后显示 Good 获胜、正确目标和原因。
- 游戏结束后才在所有座位公开最终角色。

### A3. Evil 胜利：刺客命中 Merlin

重复 A2，但 Assassin 最终选择 Merlin。

预期结果：

- 刺杀命中后显示 Evil 获胜。
- 结算目标、胜利原因和最终角色正确。
- 已结算任务、投票和胜负结果不再变化。

### A4. Evil 胜利：三次任务失败

1. 创建新房间并记录 Evil 玩家。
2. 每次组队至少包含一名 Evil，五名玩家全部同意提案。
3. Good 任务队员提交 Success；至少一名 Evil 任务队员提交 Fail。
4. 重复直到三次任务失败。

预期结果：

- 5 人局任意任务出现至少一张 Fail 即失败。
- 每次任务只公开 Success/Fail 总数。
- 三次任务失败后直接显示 Evil 获胜，不进入刺杀阶段。

### A5. Evil 胜利：连续五次提案被否决

1. 创建新房间。
2. 当前队长按任务板要求选择正确人数并提交。
3. P1–P5 全部投“拒绝队伍”。
4. 检查连续否决轨道和下一任队长。
5. 重复到第 5 次否决。

预期结果：

- 每次否决后计数增加 1，队长轮换，任务序号不前进。
- 第 5 次否决后 Evil 立即获胜。
- 该路径不进入任务出牌或刺杀阶段。

## 4. 每个秘密阶段的检查方法

### 4.1 投票未结算

1. 先让一名玩家投票，其余四名暂不操作。
2. 查看全部 Profile。

预期结果：提交者看到自己的选择和等待提示；其他玩家只看到自己的可选按钮，不知道提交者投了什么。

### 4.2 任务牌未结算

1. 先让一名任务队员提交任务牌，其余任务队员暂不操作。
2. 查看全部 Profile。

预期结果：提交者只看到自己的牌和等待提示；其他玩家不知道该牌内容；非任务队员不能出牌。

## 5. Gate B：刷新与持久化重连

每个场景使用一个新房间，每次只注入一种故障。

### B1. 队长选队前刷新

1. 进入队伍提案阶段，不选择玩家。
2. 刷新当前队长的页面。

预期结果：自动恢复原座位、角色和队长权限；不要求重新加入；可以继续选队并提交。

### B2. 投票后刷新

1. 进入队伍投票阶段。
2. 只让一名玩家提交投票，然后立即刷新该 Profile。

预期结果：刷新后恢复自己的已提交选择和等待状态；不能重复投票；其他玩家仍看不到该票内容。

### B3. 任务牌后刷新

1. 进入任务阶段。
2. 只让一名任务队员提交任务牌，然后立即刷新该 Profile。

预期结果：刷新后恢复自己的任务牌和等待状态；不能重复出牌；其他玩家仍看不到该牌内容。

### B4. Node 服务重启（PostgreSQL 保持运行）

1. 在队伍提案阶段记下房间 ID、队长、任务序号和连续否决数。
2. 在终端 1 使用 `Ctrl-C` 停止 `pnpm dev:server`；不要停止 Web 或 PostgreSQL。
3. 确认客户端显示连接中断或重连状态。
4. 在终端 1 重新运行 `pnpm dev:server`。
5. 等待自动恢复；必要时点击页面“重连”。
6. 使用原 Profile 完成一次选队、投票和任务结算。

预期结果：

- 五个客户端使用原凭据回到原座位，不重新加入。
- 房间 ID、角色、任务进度和历史不变。
- 未完成阶段可以继续，不产生重复投票或任务牌。
- 重连后能完成一次完整任务，证明恢复的不只是页面路由。

### B5. PostgreSQL 服务重启

该场景要求测试者能够安全操作数据库服务。使用仓库 Compose 部署时：

1. 在队伍提案阶段记下房间 ID、角色、队长、任务序号、连续否决数和已结算历史。
2. 在终端 1 使用 `Ctrl-C` 停止 `pnpm dev:server`，避免数据库重启期间产生新写入。
3. 在 PostgreSQL 部署目录执行：

   ```bash
   docker compose restart postgres
   docker compose ps
   ```

4. 等待 `postgres` 显示 healthy。使用其他部署方式时执行等价的安全重启与健康检查。
5. 重新运行 `pnpm dev:server`，让五个客户端恢复连接。
6. 使用原 Profile 完成一次选队、投票和任务结算。

预期结果：

- PostgreSQL 重启不删除 named volume；严禁执行 `docker compose down -v`。
- 五个客户端使用原凭据恢复原房间和座位。
- 重启前记录的角色、进度、历史和秘密提交状态保持一致。
- 恢复后可以继续完成任务，且不会重复已经结算的事件。

## 6. Gate C：7–10 人 LAN

### C1. 7 人第 4 次任务的两张 Fail 规则

7 人局任务人数为 `2 / 3 / 3 / 4 / 4`，第 4 次任务需要至少两张 Fail 才失败。

运行两局，并在前三次任务得到“成功、失败、成功”，避免提前结束：

1. 第一局第 4 次任务选择 3 名 Good 和 1 名 Evil；Good 提交 Success，Evil 提交 Fail，得到 3 张 Success、1 张 Fail。
2. 第二局第 4 次任务选择 2 名 Good 和 2 名 Evil；Good 提交 Success，两名 Evil 都提交 Fail，得到 2 张 Success、2 张 Fail。

预期结果：第一局第 4 次任务成功；第二局第 4 次任务失败；公开结果仍不关联玩家。

### C2. 10 人容量与布局

1. 使用 P1–P10 加入同一个 10 人房间。
2. 在桌面和至少一台窄屏设备检查座位与中央任务板。
3. 开始游戏并完成至少一次选队、全员投票和任务结算。

预期结果：

- 十个客户端都有独立座位和凭据。
- 桌面圆桌座位不遮挡中央操作区；窄屏页面没有横向溢出。
- 10 人任务人数显示为 `3 / 4 / 4 / 5 / 5`。
- 所有客户端阶段同步，任务结算结果一致。

### C3. 真实 LAN 设备

至少将两个本地 Profile 替换为手机、平板或另一台电脑，通过主机 LAN IP 加入。

预期结果：不同设备可以创建/加入、完成动作并断线重连；控制台没有 CORS 或 Socket.IO 来源错误。

### C4. 双房间隔离

1. P1–P5 加入房间 A，P6–P10 加入房间 B。
2. 两个房间都开始游戏。
3. 只在房间 A 提交队伍、投票和一次任务。
4. 检查房间 B，再在房间 B 执行不同结果的操作。

预期结果：房间 A 的队长、提案、投票、任务历史和结果都不会出现在房间 B，反之亦然。

## 7. 通过条件与记录

- Gate A 的四种结束路径全部通过，才能记录“5 人游戏流程通过”。
- Gate B 全部通过，才能分别记录“Node 服务重启恢复通过”和“PostgreSQL 服务重启与凭据重连通过”。
- Gate C 全部通过，才能记录“5–10 人真实 LAN 验收通过”。
- 每完成一项，把房间 ID、日期、设备/Profile、结果和异常写入测试记录，再更新 `docs/PROJECT_STATUS.md`；不要仅根据自动化测试勾选人工验收项。
